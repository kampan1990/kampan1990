Critical rule: TotTP fires → PairTP and SepTP do NOT run that tick.
PairTP fires → SepTP does NOT run.
TPAll and RunTP run independently regardless of ChkAllTP result.
All 3 systems can fire the same tick: ChkAllTP fires SepTP(M1), then ChkTPAll also fires, then RunTP fires.
⚠ Redesign Issue #1: SepTP, TPAll, RunTP can all fire on the same tick independently. If SepTP(M1) closes M1 winners, then TPAll also tries to close remaining M1 positions, then RunTP closes runners — 3 sequential closes in one tick can create unintended outcomes.

⚠ Redesign Issue #2: ChkAllTP returns after first fired priority, but ChkTPAll and ChkRunTP still run. Consider: if TotTP fires, should TPAll be skipped that tick?

Key insight: GetBestProfit returns winners sorted best→worst. SKCount top winners become "survivors" (get BE SL). Only winners ranked SKCount onward are "closeable".

Absorption safety: Each step of absorption checks: CGP must still cover (req + total_absorbed_so_far + next_loser). If any single loser is too large, the loop breaks — that loser stays open for the next TP round.

AbsorbN=0: Try to absorb ALL affordable losers. AbsorbN=N: Cap at N per round (gradual reduction strategy).
⚠ Current Architecture Issues Found:
# Issue Risk Fix
1 ChkAllTP + ChkTPAll + ChkRunTP all fire same tick independently Triple close in one tick — unexpected behavior Use single bool: if(ChkAllTP()) return; prevents TPAll from double-closing
2 SepTP closes M1, M2, M3 all in same call (sequential) If M1 TP fires and closes M1 winners, M2 TP also checks independently No real problem here — each is independent DoTP with its own CGP check
3 UpdateRunners refreshes every tick — runners change dynamically A runner in gRunTk1 now may not be a runner next tick if better one appears Consider: once designated, keep runner until its SL is hit or RunTP fires
4 RunTP fires independently — doesn't coordinate with ChkAllTP ChkAllTP fires, closes regular positions; RunTP also fires same tick, closes runners Minor — runners are separate pool. Generally OK.
5 AbsorbN=0 absorbs ALL affordable losers in one round Can wipe out large loser pile if CGP is large — sudden large realized loss even if net positive Recommend: set AbsorbN=1-3 for controlled reduction. User controls via input.

✅ Key Change in Proposed Design:
TPAll becomes Priority 4 in the same priority chain — if TotTP/PairTP/SepTP already fired, TPAll is skipped. Prevents "double close" scenario where both SepTP and TPAll fire on same tick.

RunTP stays independent (different position pool — runners only close via their own TP target).

Priority chain: TotTP → PairTP → SepTP → TPAll → skip
Only ONE level fires per tick. Clear, predictable, safe.
Additional Recommendations:
• AbsorbN: Default 1-2 (not 0). Controlled gradual reduction is safer than all-at-once.
• SKCount: Set to 1-2 survivors per magic to lock profit and keep some exposure.
• RunKeepN: Consider "sticky runners" — once designated, keep until SL hit (not re-evaluated every tick).
• TPPair threshold: Should be higher than SepTP max — otherwise PairTP never triggers (SepTP fires first).
• TPTot threshold: Should be > TPPair which should be > max(TP1,TP2,TP3).
